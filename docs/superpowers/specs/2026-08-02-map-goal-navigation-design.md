# 地图终点权威、可靠到达与防空转导航设计

日期：2026-08-02

状态：详细设计已确认，待用户审阅本文后进入实施计划

适用范围：FastAPI Dashboard、TaskOrchestrator、共享迷宫核心、Webots 仿真适配器和真实小车适配器

## 1. 目标

自动探索任务必须始终使用所选不可变地图版本保存的终点。以当前
`Task12 公网验收迷宫 · v2` 为例：

- 起点是 `(0,4)`，初始方向为 `N`。
- 地图终点是 `(4,0)`。
- 自动探索页面只显示并锁定 `(4,0)`。
- 页面或旧 API 不能用 `(0,3)` 等手工坐标覆盖自动任务终点。
- 小车只有在可靠定位证据确认到达 `(4,0)` 后，才能进入
  `COMPLETED / goal_reached`。

手工坐标只属于“单步调试”，不能参与自动任务的终点判定。

## 2. 已确认问题

当前自动任务创建接口接受客户端提交的 `goal`。页面曾把手工目标
`(0,3)` 写入任务。小车从地图起点 `(0,4)` 前进一步后，逻辑位置正好变为
`(0,3)`，于是系统在第 1 步发出 `step.goal_reached` 并完成任务。

因此截图中的“车开到墙边就停住”并不是路径已经走完，而是客户端目标覆盖了
地图终点，形成了错误的成功判定。

另一个已经观测到的风险是：

- 编码器等效前进约 `450 mm` 时，物理位姿可能只移动约 `365 mm`。
- 仅凭编码器动作 `done` 推进逻辑格子，会积累物理位置误差。
- 继续运行可能越界、碰墙或触发 `OBSTACLE_TOO_CLOSE`。

本设计同时修复终点权威和“编码器完成不等于车体确实到格”的问题。

## 3. 范围

### 3.1 本轮包含

1. 自动任务终点从不可变地图版本解析，客户端不能覆盖。
2. 自动页面显示地图终点并锁定目标字段。
3. 单步调试与自动探索彻底分离。
4. 使用地图合法通道生成到终点的路线。
5. 每个动作等待相同 `action_id` 的 `done` 或 `error`。
6. 使用编码器、三向 ToF、可用时的 IMU 和墙面约束验证动作结果。
7. 对欠行程、偏航和可恢复滑移执行有限、可审计的动作级修正。
8. 地图与传感器冲突时安全停车，不把冲突误判为任务完成。
9. 完整记录路线、动作、定位证据、修正、参数版本、成绩和回放。
10. 增加从 `(0,4)` 真实走到 `(4,0)` 的 Webots P5 验收。

### 3.2 本轮不包含

- 不训练大模型。
- 不使用 Webots 真值参与规划或定位融合。
- 不让服务器或 RDK 发送高频左右轮 PWM。
- 不降低急停、前方过近、心跳超时或动作超时阈值。
- 不让自动调参静默修改安全参数或任务完成阈值。
- 不把仿真通过表述成真实小车已经通过。
- 不新增不规则迷宫、斜墙或曲线墙支持。

## 4. 核心规则

### 4.1 地图是自动终点的唯一权威

自动任务创建时，后端必须用 `map_version` 读取不可变地图定义和摘要，解析
`definition.goals`。自动页面提交的坐标不参与解析。

任务保存一份不可变终点快照：

```json
{
  "type": "map_goal",
  "cell": [4, 0],
  "candidate_cells": [[4, 0]],
  "source_map_version": "mapv-...",
  "source_map_digest": "...",
  "resolution": "single"
}
```

该快照写入任务记录、运行 metadata 和 JSONL 事件。任务创建后，即使用户在
页面切换地图，也不能改变旧任务的地图或终点；页面必须创建新任务。

### 4.2 多终点地图的确定性规则

地图编辑器继续允许保存一个或多个终点：

1. 只有一个终点时直接采用。
2. 有多个终点时，从地图起点计算合法通道中的最短格子路径。
3. 采用最短可达终点。
4. 路径长度相同时，按 `(y, x)` 升序选择，保证固定输入得到固定结果。
5. 没有可达终点时预检失败，不创建运行。

页面同时显示候选终点和本次自动任务解析出的主终点。

### 4.3 自动任务禁止手工覆盖

主 Dashboard 创建自动任务时只允许：

```json
{
  "run_kind": "auto_to_map_goal",
  "mode": "simulation",
  "map_version": "mapv-...",
  "param_version": "1",
  "physical_profile_id": "normal-v1"
}
```

兼容旧客户端时，如果 `run_kind=auto_to_map_goal` 仍提交
`goal.type=cell`，后端返回 `400 AUTO_GOAL_OVERRIDE_FORBIDDEN`，不能静默忽略，
避免操作者误以为手工值已生效。

`exploration_complete` 只保留给明确标记的内部批量测试或完整建图任务，不作为
网站“开始自动探索”的默认行为。

## 5. 页面设计

### 5.1 自动探索面板

现有“目标格”改为“地图终点（自动）”：

- X、Y 字段使用只读显示，不可输入。
- 显示来源地图名称、版本和摘要短码。
- 当前 v2 显示 `X 4 / Y 0`。
- 地图切换后，先读取新版本定义，再更新终点显示。
- 地图定义、摘要或终点加载失败时，禁止预检和开始。
- 页面不得从缓存的旧任务目标回填地图终点。

预检结果必须明确显示：

- 起点和方向。
- 解析后的主终点。
- 可达路径格数。
- 地图摘要是否与 Webots/RDK 已加载摘要一致。
- 物理净通道检查结果。

### 5.2 单步调试面板

手工坐标和动作移入独立的“单步调试”折叠区。该区域必须明确提示：

> 单步调试不会改变自动任务终点，也不会触发自动任务完成。

单步调试可以发送前进一格、左转、右转、掉头、停止，以及后续受限的微调动作。
每个动作仍须有 `action_id`、`ack` 和对应的 `done` 或 `error`。

单步调试不得复用自动任务的 `goal_reached` 判定器。

## 6. 后端组件

### 6.1 MapGoalResolver

新增单一职责组件 `MapGoalResolver`：

- 输入：`map_version`。
- 依赖：地图版本仓库和地图校验器。
- 输出：地图摘要、候选终点、主终点、解析规则和最短路径长度。
- 不访问串口，不改变地图，不写任务状态。

解析时再次检查：

- 地图版本存在且不可变。
- 摘要与定义内容匹配。
- 起点和所有候选终点在边界内。
- 至少一个终点可达。

### 6.2 TaskOrchestrator

`TaskOrchestrator.create_task` 对自动任务执行以下顺序：

1. 校验模式、地图版本、参数版本和物理配置。
2. 拒绝客户端 `cell` 目标覆盖。
3. 调用 `MapGoalResolver`。
4. 把解析结果保存为任务终点快照。
5. 发出 `task.created`，其中包含终点来源证据。

`_goal_for` 不再只检查一个客户端坐标，而是创建地图终点验证器。完成事件必须同时
满足第 9 节的逻辑到达和物理证据条件。

### 6.3 GoalDirectedPlanner

自动到终点任务使用目标导向规划器：

- 输入：不可变地图几何、当前可靠格子、当前方向和主终点。
- 输出：动作级路线，包括转向和逐格前进。
- 基线算法使用 BFS 计算最少格子路径。
- 相同长度路径按固定方向优先级选择，保证固定地图、参数和随机种子可复现。
- 不直接访问串口，也不读取 Webots 真值。

原 DFS `MazePlanner` 保留给完整建图模式。自动到终点任务不能因 DFS 栈耗尽而
误报成功；路径耗尽但尚未到达终点时返回 `NO_PATH`。

### 6.4 MotionEvidenceGate

新增动作证据门：

- 输入：计划动作、对应 `done/error`、编码器、ToF、可选 IMU、连续位姿估值、
  墙面约束和参数版本。
- 输出：`accepted`、`recoverable` 或 `unsafe`。
- 不直接发送动作；只给 `MazeRunner` 结构化判定和修正建议。

地图格子只在 `accepted` 后推进。`error`、超时、低置信度或物理证据冲突时不推进。

## 7. 动作执行数据流

每个计划动作执行以下闭环：

1. 规划器生成动作和期望终态。
2. `MotionTargetResolver` 根据地图格尺寸和当前参数生成目标。
3. 适配器发送唯一 `action_id`。
4. 等待同一 `action_id` 的 `ack`。
5. ESP32 或仿真控制器在本地闭环执行。
6. 等待同一 `action_id` 的 `done` 或 `error`。
7. `PoseFusion` 更新连续位姿估值。
8. `MotionEvidenceGate` 比较逻辑期望与物理证据。
9. 证据通过后才推进格子；可恢复时先执行有限修正；不安全时停车。
10. 重新检查终点条件，再规划下一步。

禁止在发送动作后立即更新格子。禁止收到不匹配 `action_id` 的结果后推进状态。

## 8. 空转、滑移与方向修正

### 8.1 证据来源

仿真和实车使用相同的算法输入：

- 左右编码器和轮速。
- 前、左、右 ToF。
- 可用时的 IMU yaw、yaw rate。
- 已保存地图的墙面约束。
- 上一步可靠位姿和动作期望。

Webots `sim_truth` 只用于计算误差、评分和验收，不得进入 `PoseFusion`、
`MotionEvidenceGate` 或规划器。

真实小车没有 IMU 时允许降级使用编码器、三向 ToF 和墙面约束。证据不足时停止并
报告 `POSE_UNCERTAIN`，不能伪造航向或强行完成任务。

### 8.2 固定任务完成阈值

下列阈值随参数版本冻结，并写入运行 metadata：

```yaml
arrival_verification:
  nominal_position_error_ratio: 0.10
  recoverable_position_error_ratio: 0.20
  nominal_heading_error_deg: 8
  recoverable_heading_error_deg: 12
  goal_min_confidence: 0.80
  max_recovery_attempts_per_cell: 2
```

这些是任务验收阈值，不属于自动调参项。模型、强化学习和规则型自动调参都不能在
运行中修改。

### 8.3 判定

- `accepted`：位置误差不超过格长的 10%，方向误差不超过 8°，且定位置信度不低于
  0.80。
- `recoverable`：位置误差不超过格长的 20%，方向误差不超过 12°，且有足够墙面或
  IMU 证据支持修正。
- `unsafe`：误差超过可恢复范围、置信度不足、传感器与地图冲突、编码器显示运动但
  车体证据显示空转，或超过修正次数。

观测到的 `450 mm -> 365 mm` 欠行程约为 18.9%，属于可恢复区间，不能直接当作正常
到格，也不能立即推进下一格。

### 8.4 有限修正动作

可恢复偏差转换为动作级命令，而不是高频 PWM：

- `nudge_forward`：修正剩余直线距离，单次不超过 0.25 格。
- `align_heading`：修正方向，单次不超过 15°。
- 修正速度不超过当前基础速度的 50%。
- 每格最多修正 2 次。
- 每次都有独立 `action_id`、`ack`、`done/error` 和证据复核。

修正失败、重复空转或达到次数上限时停车，任务进入 `ERROR`，错误码为
`MOTION_RECOVERY_FAILED`。不得通过增加 PWM 上限或降低障碍阈值强行通过。

## 9. 终点完成判定

`goal_reached` 必须同时满足：

1. 任务的不可变主终点来自当前 `map_version`。
2. 规划逻辑位置等于主终点。
3. 最近一个移动或修正动作收到匹配 `action_id` 的成功 `done`。
4. 可靠主定位格等于主终点。
5. 连续位姿落在终点格允许范围内。
6. 定位置信度不低于 0.80。
7. 当前没有地图传感器冲突、急停、设备断联或未处理动作错误。

只有上述条件全部通过，才能按顺序写入：

1. `step.goal_verified`
2. `task.finalizing`
3. 成绩和回放清单
4. `task.completed`，原因 `goal_reached`

新运行停止产生 `step.goal_reached`，统一写入 `step.goal_verified`。回放读取器只在
展示历史运行时把旧 `step.goal_reached` 映射为“旧版逻辑到达”，并明确标注它没有
新版物理证据，避免“逻辑坐标相等”被理解为已经物理到达。

## 10. 地图与传感器冲突

不可变地图墙体和实时观测墙体必须分层保存：

- `planned_walls`：地图版本中的权威几何，规划使用。
- `observed_walls`：ToF 当前观测和置信度，定位与诊断使用。

实时 `observe` 不得覆盖不可变的 `planned_walls`。

当地图标记为开放通道，但前向 ToF 连续 3 个有效样本低于当前墙体阈值时：

1. 不发送前进动作。
2. 立即发出动作级停止。
3. 写入 `map_sensor_conflict` 证据。
4. 任务进入 `ERROR / MAP_SENSOR_CONFLICT`。

该错误要求操作者检查地图版本、Webots 加载摘要、实体墙体、ToF 安装和测距质量。
系统不得自动删除地图墙体或降低安全阈值。

## 11. 事件、成绩与回放

新增或补强以下不可变事件：

- `task.goal_resolved`
- `route.planned`
- `action.dispatched`
- `action.acknowledged`
- `action.completed`
- `motion.evidence_evaluated`
- `motion.recovery_requested`
- `motion.recovery_completed`
- `pose.corrected`
- `map_sensor_conflict`
- `step.goal_verified`
- `task.completed`

每个事件至少记录：

- `task_id`、`run_id`、`map_version`、地图摘要。
- `param_version`、物理配置摘要和固定随机种子。
- 计划格、可靠格、连续位姿、方向和置信度。
- `action_id`、动作名称、目标、结果和耗时。
- 编码器、ToF、可用时的 IMU。
- 修正前后误差、修正理由和次数。

成绩与回放必须能解释：

- 走了哪条路线。
- 在哪里发生空转、滑移或偏航。
- 系统做了什么修正。
- 最终为何确认到达或为何安全停止。

## 12. 错误处理

| 错误码 | 条件 | 状态与处理 |
| --- | --- | --- |
| `AUTO_GOAL_OVERRIDE_FORBIDDEN` | 自动任务提交手工目标 | 400，不创建任务 |
| `MAP_GOAL_MISSING` | 地图没有终点 | 预检失败 |
| `MAP_GOAL_UNREACHABLE` | 没有可达终点 | 预检失败 |
| `MAP_DIGEST_MISMATCH` | 任务、适配器或地图定义摘要不同 | 禁止重置和开始 |
| `NO_PATH` | 规划器不能到终点 | 停车并进入 ERROR |
| `ACTION_RESULT_MISMATCH` | `done/error` 的 `action_id` 不匹配 | 停车并进入 ERROR |
| `POSE_UNCERTAIN` | 定位证据不足 | 停车并进入 ERROR |
| `WHEEL_SLIP_DETECTED` | 编码器运动但车体证据不足 | 进入有限修正或停车 |
| `MOTION_RECOVERY_FAILED` | 有限修正失败或超限 | 停车并进入 ERROR |
| `MAP_SENSOR_CONFLICT` | 地图开放方向被稳定测为墙 | 停车并进入 ERROR |

急停、心跳超时、动作超时、前方过近和设备断联继续使用现有更高优先级保护。

## 13. 失败测试优先的验证设计

实现必须严格执行“失败测试 → 最小实现 → 定向测试 → 完整回归 → 独立提交”。

### 13.1 后端测试

1. 自动任务提交 `goal.cell=[0,3]` 时失败，且不写任务或运行。
2. 单终点地图稳定解析 `(4,0)`。
3. 多终点地图按最短路径和 `(y,x)` 决胜规则解析。
4. 地图切换会创建新任务，不改变旧任务终点快照。
5. 地图摘要不匹配时不能重置或开始。
6. `_goal_for` 不能只凭逻辑格相等完成。
7. 不匹配的 `action_id` 不能推进格子。
8. 规划器能从 `(0,4)·N` 绕过内部墙到 `(4,0)`。
9. 路径耗尽但未到终点时返回 `NO_PATH`。

### 13.2 运动证据测试

1. 编码器达标但物理位姿不动时判定空转，不推进格子。
2. `450 mm -> 365 mm` 欠行程进入可恢复流程。
3. 有限修正成功后只推进一次格子。
4. 修正两次仍失败时进入 `MOTION_RECOVERY_FAILED`。
5. 转向编码器达标但航向不足时不能接受。
6. 没有 IMU 时使用 ToF 和墙面约束降级；证据不足时报
   `POSE_UNCERTAIN`。
7. `sim_truth` 变化不能改变算法输出。
8. 地图开放方向连续 3 次测为墙时触发 `MAP_SENSOR_CONFLICT`。

### 13.3 页面测试

1. 自动页面显示地图终点 `(4,0)`，字段为只读。
2. 地图切换后终点、摘要和路径长度同步刷新。
3. 终点加载失败时预检和开始按钮禁用。
4. 主面板不再从手工字段构造 `goal.cell`。
5. 单步调试明确标记，动作不会触发自动完成。
6. 急停始终可见且两种模式都可用。

### 13.4 完整回归

- `python3 -m compileall rdk_maze_tuner`
- `python3 -m pytest rdk_maze_tuner/tests -q`
- `pio run`
- Dashboard JavaScript 语法检查。
- Webots P1–P4 现有物理验收。
- HTTPS 登录、控制权、急停、回放和服务重启回归。

## 14. P5 终点到达验收

新增正式 P5，使用 `Task12 公网验收迷宫 · v2`：

1. 预检显示起点 `(0,4)·N`、终点 `(4,0)` 和正确地图摘要。
2. 重置后编码器、计时器、路径和任务状态归零。
3. 点击一次“开始自动探索”后不再输入手工目标。
4. 小车沿合法通道运行，至少完成一次转向。
5. 全程不越界、不穿墙、不碰撞。
6. 欠行程或偏航时出现可解释的修正事件。
7. 页面持续显示可靠格、连续厘米坐标、车头方向和置信度。
8. 最终可靠格为 `(4,0)`，任务为 `COMPLETED / goal_reached`。
9. 回放包含完整路线、动作、修正、参数版本、物理配置和成绩。
10. 固定地图、参数、物理配置和随机种子重复运行，结果可复现。

P5 失败时不得发布“已经实现走到终点”的结论。

## 15. 部署与回滚

1. 在隔离候选服务上运行失败测试和完整回归。
2. 候选环境完成 P1–P5。
3. 保存候选 release、提交哈希、地图摘要和验收 run_id。
4. 原子切换正式 release。
5. 通过 `https://8.ilelezhan.cn` 完成登录、预检、开始、到达、成绩和回放验收。
6. 任一关键检查失败，切回上一稳定 release。

部署不开放新的公网串口、Webots 控制或 VNC 端口，不记录密码、密钥或真实设备路径。

## 16. 真实小车边界

仿真 P5 通过只证明 Webots 闭环、网站交互和算法逻辑通过。真实小车还必须按顺序
完成：

1. 三向 ToF 方向和量程检查。
2. 左右编码器方向检查。
3. 低速电机方向检查。
4. 10 cm、单格和 90° 标定。
5. 急停、心跳超时、前方过近和动作超时检查。
6. 2×2 或 3×3 简单迷宫检查。
7. 当前 v2 地图完整到终点检查。

只有真实 RDK X3、ESP32、传感器和电机均在线，并有实际遥测、动作与现场证据时，
才能标记“真实小车通过”。
